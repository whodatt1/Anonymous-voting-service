# 📊 프로젝트 명: 고성능 실시간 익명 투표 시스템

## 1. 프로젝트 개요
- **서비스 주제:** 로그인 없이 고유 URL 공유만으로 빠르게 접근 가능한 실시간 익명 투표 서비스
- **개발 목적:** B2C 서비스 기업이 요구하는 '대규모 트래픽 정합성(동시성 제어)', '실시간 통신 최적화', '모던 아키텍처 설계' 역량 학습 및 포트폴리오 구축
- **핵심 정책:** 모든 기술적 의사결정 및 코드 작성은 AI와의 개념 학습 및 토론을 선행한 후, 개발자가 직접 주도하여 검증하고 적용한다.

## 2. 핵심 비즈니스 로직 및 UX
- **로그인 없는 접근성 (Frictionless UX):** 투표 생성자와 참여자 모두 회원가입/로그인 과정이 생략된다.
- **URL 기반 공유:** 투표 생성 시 DB PK 대신 짧은 랜덤 코드(shareCode)를 발급하여 `/votes/{shareCode}` 형태의 URL로 공유한다. DB PK 노출과 순차 접근 시도를 방지한다.
- **비회원 식별 전략:**
    - **participantToken:** 첫 접근 시 UUID를 발급하여 HttpOnly 쿠키(Max-Age = 투표 만료까지 남은 초, 즉 expiresAt - 현재 시각으로 동적 계산)로 저장. 중복 투표 방지의 식별자로 활용한다.
    - **hostToken:** 투표 생성 시 UUID를 발급하여 관리 URL(`/votes/{shareCode}/manage?hostToken={UUID}`)에 포함한다. 쿠키가 아닌 URL 자체가 영구 인증 수단이 되므로 만료 문제가 없다.
- **역할 기반 커넥션 분리 (서버 부하 최적화):**
    - **생성자(Host):** 투표 결과를 모니터링하는 관리자 화면에만 **SSE(Server-Sent Events)**를 적용하여 실시간 애니메이션/집계 현황을 제공한다.
    - **참여자(Participant):** 투표 제출 시 1회성 REST API 요청만 수행하여 서버의 커넥션 고갈을 방지한다.
- **결과 공개 정책:** 투표 결과는 항상 공개이다. 투표 여부와 무관하게 shareCode를 아는 누구나 현재 집계를 조회할 수 있다. 참여자 결과 조회는 SSE가 아닌 REST 스냅샷으로 제공한다(SSE는 Host 전용 유지). 무한 새로고침 방지를 위해 결과 조회 엔드포인트에도 Rate Limiting을 적용한다.
- **집계 구조 (Redis + DB 이중화):** 실시간 집계는 Redis INCR로 관리하고, 매 투표 시 VoteRecord를 DB에 INSERT하여 영속성을 보장한다. 결과 조회 시 Redis를 우선 참조하고, Redis 장애 시 DB의 COUNT(*) 집계로 폴백한다. VoteOption에 count 컬럼을 두지 않아 동시 업데이트 경합을 방지한다.
- **어뷰징 방지:** 비회원 상태에서의 중복 투표를 방지하기 위해 participantToken(UUID)을 식별자로 활용한다. Redis를 1차 방어선(빠른 중복 체크), DB의 UNIQUE 제약 `(poll_id, participantToken)`을 2차 방어선으로 둔다. 이는 "한 사람이 같은 투표에 여러 번 투표하는 것"을 막는 로직이며, "누군가 서버에 과도한 요청을 퍼붓는 것"을 막는 레이트 리미팅과는 별개의 문제다(레이트 리미팅은 3번 섹션의 "배포 목표 → 트래픽 폭주 대응" 참조).

## 3. 기술 스택 및 모듈 구성
- **Backend Core:** Java 21 / Spring Boot 3.x / JPA
- **Frontend:** React. 백엔드 지원자 포지션이므로 프론트는 시연을 위한 보조 영역으로 취급한다. **디자인(레이아웃, 스타일링, 색상, 애니메이션)은 AI에게 전적으로 맡긴다.** 반면 **내부 동작(훅 사용, 상태 관리, 특히 SSE(`EventSource`) 수신 후 화면을 실시간 갱신하는 로직)은 직접 학습하며 작성**한다 — 이 부분은 백엔드와의 연동 지점이라 면접에서 직접 설명할 수 있어야 하는 영역이다. 프론트 영역에서도 4번 섹션의 3단계 워크플로우(설계 토론→ADR→직접 코딩)를 동일하게 적용하되, 디자인은 예외로 AI가 전담한다.
- **합류 시점:** 프론트는 백엔드보다 늦게 시작한다. Phase 0의 핵심 API(투표 생성/참여/SSE 스트리밍)가 동작을 마친 시점에 합류시킨다. 이후 Phase 1(헥사고날 조건부 적용)·Phase 2(프로세스 분리)는 API의 외부 스펙(URL, 요청/응답 형태)을 바꾸지 않는 내부 리팩토링에 가까우므로, 한 번 합류한 프론트는 그 변화에 큰 영향을 받지 않는 구조를 목표로 한다.
- **Data & Concurrency:** MySQL / Redis (Atomic INCR, Cache, Duplicate Check)
- **DevOps & Monitor:** Docker / GitHub Actions CI (배포는 별도 전략 참조) / Prometheus + Grafana
- **아키텍처 전략:** 단일 모놀리식 + 레이어드 아키텍처(Phase 0)로 시작한다. 동시성 테스트 비교 실험 결과에 따라 헥사고날로 조건부 전환(Phase 1, 모듈 구조는 그대로 유지)하고, 이후 SSE의 NIO 커넥션 고갈로 인한 서비스 영향이 실측되면 `vote-push`를 Netty 기반 별도 프로세스로 분리한다(Phase 2, 이때 비로소 Gradle 멀티모듈도 함께 적용). ※ 부하 테스트 결과 SseEmitter는 AsyncContext/NIO 처리로 Tomcat 스레드를 점유하지 않음이 확인됨 — 실제 병목은 NIO 커넥션 수(max-connections 기본 8192). "모듈 분리"는 독립적인 목적이 아니라 "프로세스 분리를 위한 전제 조건"으로 취급한다. 상세는 하단 "Architecture Strategy" 참조.
- **배포 목표 (AWS, 프리 티어 우선):** AWS에 배포하며, 1차 목표는 프리 티어 범위 내 운영이다.
  - **프리 티어 과금 기준:** 비용은 "EC2/RDS/ElastiCache 등 인스턴스 개수·타입"을 기준으로 발생하며, "한 EC2 인스턴스 안에서 몇 개의 포트(프로세스)를 띄우는지"는 직접적인 과금 기준이 아니다. 즉 Phase 2에서 `vote-api`와 `vote-push`를 분리해도, **같은 EC2 인스턴스 안에서 서로 다른 포트로 띄우는 한 추가 비용이 발생하지 않는다.** 비용이 늘어나는 경우는 `vote-push`를 위해 별도의 EC2 인스턴스를 새로 띄울 때뿐이며, 이는 의도한 방향이 아니므로 지양한다.
  - **계정 정책 확인 (필수, 가장 먼저):** AWS는 2025년 7월 15일을 기준으로 프리 티어 정책이 변경되었다.
    - 2025-07-15 이전 가입 계정: 레거시 정책 — EC2/RDS/ElastiCache 각각 750시간/월, 12개월간 적용.
    - 2025-07-15 이후 가입 계정: 가입 시 **무료 플랜 / 유료 플랜**을 선택해야 한다. 무료 플랜은 최대 200달러 크레딧을 6개월간 사용하고 소진 시 자동 정지(과금 없음, 단 계정이 비활성화되고 리소스가 삭제될 위험이 있음). **유료 플랜은 크레딧 소진 시 자동 정지되지 않고 표준 종량 과금이 그대로 적용**되므로, 의도와 다르게 유료 플랜으로 가입/전환되어 있지 않은지 콘솔에서 반드시 확인한다.
    - **"Free tier eligible" 표시의 함정:** 인스턴스 생성 화면의 이 표시는 "그 인스턴스가 항상 무료"라는 뜻이 아니라 "프리 티어 혜택 대상 스펙 분류"일 뿐이다. 실제로는 사용 시간만큼 항상 요금이 계산된 뒤, Billing 단계에서 할인(레거시) 또는 크레딧 차감(신규 무료 플랜)이 적용되는 구조다. 여러 리소스(EC2+RDS+ElastiCache)를 동시에 켜두면 신규 정책의 200달러 크레딧이 예상보다 빠르게 소진될 수 있다.
  - **비용 방어선 (자동 차단 우선, 알림만 믿지 않음):** 사용량 모니터링은 하루 3회만 갱신되어 실시간이 아니므로, 알림보다 "자동으로 멈추는" 장치를 우선한다.
    - AWS Budgets에 예산 알림(80% 도달 시 메일) + 가능하면 임계값 도달 시 EC2 중지 등 자동 작업(Action)까지 연결한다.
    - 배포 직후 가장 먼저 설정하는 작업으로 취급한다(코드 작업보다 우선).
  - **트래픽 폭주 대응 (투표 시스템 특성상 중요):** 이 프로젝트는 "고유 URL 공유"가 핵심 UX이므로, 공유 URL이 예상보다 널리 퍼지는 정상적인 트래픽 폭증과, 악의적 트래픽(무한 새로고침, 동시 SSE 연결 남발)을 둘 다 염두에 둬야 한다. 둘 다 비용·가용성 측면에서는 동일하게 위험하다.
    - **레이트 리미팅:** IP당 분당 요청 수를 제한한다(예: Bucket4j/Resilience4j + Redis 카운터). 기존 "Redis 활용 중복 투표 방지" 로직과 같은 인프라를 재사용할 수 있다.
    - **SSE 동시 커넥션 수 제한:** 호스트 모니터링용 SSE 엔드포인트에 동시 연결 가능 수의 상한을 둔다. 무제한 연결은 Phase 0에서 관찰하려는 "스레드 풀 점유" 문제를 의도와 무관하게 너무 빨리, 너무 위험하게 재현시킬 수 있다.
    - **부하 테스트 시 주의:** Phase 0의 스레드 풀 관찰 실험(부하 테스트)은 실제 EC2/RDS 사용 시간과 데이터 전송량을 인위적으로 튀게 만든다. 가급적 로컬 환경에서 먼저 검증하고, 실제 배포 환경에서 부하 테스트를 할 경우 직후 Billing 대시보드에서 사용량을 확인한다.
- **CI/CD 전략: CI는 지금부터, CD(배포)는 최후순위:** CI(빌드+테스트 자동화)와 CD(배포 자동화)는 분리해서 적용한다.
  - **CI는 배포와 무관하게 즉시 적용:** PR 생성 시 GitHub Actions가 `./gradlew test`(단위 테스트 + Testcontainers 기반 통합 테스트)를 자동 실행하고, 실패 시 머지를 막는다. Docker 이미지 빌드까지도 "배포"가 아니라 "빌드 자동화"이므로 CI에 포함해 먼저 구축한다. 이는 Phase 0부터 테스트가 쌓이는 시점에 맞춰 바로 시작한다.
  - **CD(AWS 배포)는 최후순위로 미룬다:** 비용·보안 부담이 가장 큰 단계이므로, Phase 0~2의 핵심 기술 검증(동시성 테스트, 헥사고날 비교 실험, 부하 테스트를 통한 스레드 풀 관찰)을 로컬 환경에서 모두 마친 뒤 마지막에 진행한다.
  - **배포를 미뤄도 프로젝트 핵심 가치는 유지된다:** project.md의 개발 목적(대규모 트래픽 정합성, 실시간 통신 최적화, 모던 아키텍처 설계)을 증명하는 핵심 증거(동시성 테스트 결과, 비교 실험 기록, 로컬 부하 테스트의 Grafana 캡처, CI 통과 기록)는 모두 로컬 환경과 CI만으로 확보 가능하다. 배포가 빠지면 "실제 운영 환경에서 살아있는 서비스를 보여줄 수 있는가"라는 한 가지 매력만 줄어들 뿐, 기술적 깊이를 보여주는 나머지는 영향받지 않는다.
  - **다만 최소 목표는 유지한다:** "최후순위로 미룬다"가 "포기한다"가 되지 않도록, 최소한 Phase 0이 안정화된 시점에는 1회 배포해 살아있는 URL을 만드는 것을 최소 목표로 둔다. 그 이후 Phase 1/2 완료 시점의 재배포는 일정에 따라 선택적으로 진행한다.

## 4. AI 협업 및 개발 원칙 (Ground Rules)

### 🚨 AI 페어 프로그래밍 워크플로우 (가장 중요)
Claude(또는 AI)와 협업할 때 단순히 완성된 코드를 생성하게 두지 않고, 포트폴리오의 기술적 깊이를 확보하기 위해 반드시 다음 **3단계 프로세스**를 강제한다.

1. **[1단계] 설계 토론 및 대안 분석 (Tech Spec & Trade-off):**
  - 구현할 기능의 아키텍처, DDD 규칙, 발생 가능한 예외 상황을 AI에게 질문하여 기술적 제안을 받는다.
  - **[필수]** 특정 기술이나 패턴(예: Redis, SSE 등)을 도입할 때, AI에게 반드시 다음 항목을 요구한다.
    - **도입 배경 및 채택 이유:** 왜 이 기술이 현재 문제 해결에 가장 적합한가?
    - **대안 기술 (Alternatives):** 다른 선택지는 어떤 것들이 있는가? (예: SSE vs WebSocket, Redis INCR vs DB Lock)
    - **트레이드오프 (Trade-off):** 각 대안의 장단점과, 최종적으로 해당 기술을 선택함으로써 감수해야 할 비용이나 한계점은 무엇인가?
  - **이 프로젝트에서 다루는 개념(레이어드 아키텍처, 헥사고날 아키텍처, DDD, 멀티스레드 동시성, SSE, AWS 배포 구조 등)은 "모르는 것만 예외적으로 묻는다"가 아니라, 기본적으로 모든 새로운 개념을 본 프로젝트의 실제 모듈/코드/배포 환경에 대응시켜 설명부터 받는 것을 기본값으로 한다.** 추상적 정의를 그대로 받지 않는다. 예: "지금 Service가 RedisTemplate을 직접 의존하는 구조에서, 멀티스레드 동시성 테스트를 작성하려면 왜 어려운지 구체적으로 설명해줘." 이렇게 하면 1단계 토론 자체가 학습 세션이 되고, 이해도가 충분해진 시점에 2단계(ADR 기록)로 넘어간다.
  - **설명을 들은 후 이해가 안 되면 언제든 다시 물어봐도 된다.** "한 번에 다 이해해야 다음 단계로 넘어갈 수 있다"는 부담 없이, 이해될 때까지 반복 질문하는 것을 정상적인 흐름으로 간주한다.

2. **[2단계] 의사결정 문서화 (ADR 도출) — 기록 트리거:**
  - 1단계의 토론을 통해 본인이 충분히 기술적 맥락을 이해한 후, **이 시점을 문서 기록의 유일한 트리거로 삼는다.** 단순 탐색성 토론이나 잡담성 대화는 기록하지 않는다.
  - 기록은 두 단계로 나눠 작성한다.
    - **(a) `docs/decisions.md`에 압축 요약 append:** 아래 [의사결정 로그 작성 규칙]에 따라 5~10줄 내외로 짧게 기록한다. 이 파일은 다음 세션 시작 시 항상 가볍게 로드되는 "최신 의사결정 요약"이다.
    - **(b) 디테일이 많이 필요한 경우에 한해 `docs/adr/NNN-제목.md` 풀버전 작성:** 1단계의 대안 비교, 트레이드오프 토론 내용을 보존할 가치가 있을 때만 별도 파일로 분리한다. decisions.md에는 이 파일을 가리키는 링크만 남긴다. 평소 세션에서는 로드하지 않고 필요할 때만 참조한다.

3. **[3단계] 개발자 주도 코딩 (Developer-Driven Coding):**
  - 확립된 설계와 기술적 근거를 바탕으로, **개발자가 직접 인텔리제이 에디터에 코드를 타이핑**하고 로직을 검증한다.
  - AI는 코드를 대신 짜주는 역할이 아닌, 작성된 코드의 리뷰어(Reviewer), 리팩토링 조언자, 테스트 코드 작성 가이드 역할만 수행한다.

### 📝 의사결정 로그 작성 규칙 (`docs/decisions.md`)
- **목적:** 매 대화를 누적 기록하지 않고, 확정된 의사결정만 압축해서 쌓아 다음 세션의 컨텍스트 로딩 비용을 최소화한다.
- **기록 시점:** 대화 종료 시점이 아니라, 위 2단계(ADR 도출)가 끝나는 시점.
- **형식 (한 건당 5~10줄):**
  ```
  ## [YYYY-MM-DD] 제목 (예: SSE vs WebSocket 선택)
  - 결정: (한 줄 결론)
  - 배경: (왜 이 문제를 풀어야 했는지 한 줄)
  - 대안: (검토했던 다른 선택지 1~2개, 짧게)
  - 채택 이유 / 트레이드오프: (왜 이걸 골랐고 무엇을 포기했는지 1~2줄)
  - 상세: (필요시) docs/adr/NNN-제목.md 참조
  ```
- **금지:** 토론 전문을 그대로 옮기거나, 코드 스니펫 전체를 포함하지 않는다. 압축된 결론과 근거만 남긴다.
- **파일 분리 기준:** decisions.md가 과도하게 길어지면(예: 분기/연 단위) `docs/decisions-2026.md` 식으로 연 단위 분리만 허용하고, 그 외에는 단일 파일 누적을 유지한다.

### 🧪 테스트 및 배포 원칙
- **Test First:** CI 파이프라인의 핵심인 테스트 코드를 반드시 작성한다.
  - **단위 테스트(Unit Test):** 순수 도메인 로직(예: 투표 마감 시각 검증, 옵션 개수 제약, 중복 투표 판정 규칙 등)을 Redis/DB 없이 빠르게 검증한다. Mock/Fake로 충분히 검증 가능한 영역이며, 개발 중 가장 먼저, 가장 자주 실행한다.
  - **통합 테스트(Integration Test):** 비회원 중복 투표 방지 및 Redis 동시성 제어처럼 인프라(Redis/DB)의 원자성·실제 동작이 검증의 핵심인 영역은 Testcontainers 등으로 실제 인프라를 띄운 멀티스레드 통합 테스트로 검증한다. 단위 테스트로는 레이스 컨디션을 잡을 수 없으므로 이 영역은 통합 테스트가 필수다.
  - 두 테스트는 검증 대상이 다르므로 양립한다. "통합 테스트만 있으면 충분하다"고 단정하지 않는다.
- **Fail Fast:** 컴파일 단계와 빌드 단계에서 의존성 오염(예: core가 api를 참조하는 현상)을 발견할 수 있도록 Gradle 모듈 간의 가시성을 철저히 격리한다. (모듈 분리가 적용되는 Phase 2 이후 해당)

## Architecture Strategy

### 전체 전략: 두 가지 전환을 독립적인 슬라이더로 분리
이 프로젝트에는 서로 다른 두 가지 전환이 있고, **하나가 다른 하나의 전제 조건이 아니므로 독립적으로 판단한다.**
- **모듈 내부 설계 (레이어드 ↔ 헥사고날):** "느낌"이 아니라 비교 실험으로 판단. Gradle 멀티모듈 여부와 무관하게, 단일 모듈 안에서도 패키지 구조(domain/adapter)만으로 적용 가능하다.
- **프로세스 분리 (`vote-push`를 별도 프로세스로):** SSE의 Tomcat 스레드 풀 점유가 실측되면 진행. **Gradle 멀티모듈 분리는 이 프로세스 분리를 위한 전제 조건으로만 의미를 갖는다.** 같은 프로세스 안에서 Gradle 모듈만 나누는 것은(Tomcat과 스레드 풀을 그대로 공유하므로) 스레드 풀 점유 문제를 전혀 해결하지 못해 실익이 거의 없다고 판단, 별도의 단계로 두지 않는다.
- **명칭 관련 주의:** `vote-push`를 별도 프로세스로 분리해도 Redis/MySQL을 `vote-api`와 계속 공유하므로(Database per Service 미충족), 이는 "MSA"가 아니라 "기능 분리(Service Decomposition)" 내지 "멀티 프로세스 아키텍처"로 정확히 표현한다. "MSA를 적용했다"는 과장된 표현은 면접에서 "그럼 vote-push만의 DB가 있나요?"라는 질문에 답이 약해지므로 지양한다.

[카카오페이 홈 서버의 Hexagonal Architecture 도입·제거 사례](https://tech.kakaopay.com/)를 검토한 결과, 헥사고날이 의미를 가지려면 ① 도메인 모델이 명확하고 ② 외부 의존성이 적으며 ③ 코어 모듈을 2개 이상의 컴포넌트가 재사용해야 한다는 시사점을 얻었다. 우리 프로젝트는 ①, ②는 충족하지만 ③(현재 핵심 도메인 로직을 재사용할 컴포넌트가 vote-api 하나뿐일 가능성)은 불확실하다. 또한 테스트 코드 작성 경험이 없는 상태에서는 "Mock으로 못 바꿔서 괴롭다"는 감각 자체가 형성되기 어렵다 — 비교 기준이 없으면 불편함을 느끼기 어렵다. 따라서 헥사고날 적용 여부는 **레이어드 그대로 작성한 동시성 테스트 버전과 포트/어댑터로 리팩토링한 버전을 둘 다 직접 만들어 비교**한 뒤 결정한다. 비교 결과 차이가 크지 않다면 헥사고날을 적용하지 않고 레이어드를 유지하는 것도 정당한 결론으로 취급한다.

### Phase 0: Single Monolith + Layered Architecture (시작점, Current)
- **배포 단위:** 단일 모듈, 단일 프로세스. 모듈 분리 없이 투표 생성/참여/SSE 스트리밍을 한 코드베이스에서 구현.
- **모듈 내부 구조:** Controller - Service - Repository의 전통적 레이어드 아키텍처. 포트/어댑터 분리 없이 Service가 JPA Repository와 Redis 클라이언트(RedisTemplate 등)를 직접 의존하는 가장 단순한 형태로 시작한다.
- **목적:** 아키텍처 경계를 미리 나누지 않고 가장 빠르게 동작하는 버전을 만들어, 다음을 관찰·실험한다.
  - **헥사고날 적용 여부 판단 (비교 실험):** 동시성 제어(Redis INCR 집계, 중복 투표 방지) 로직에 대해 (a) 레이어드 그대로(Service가 RedisTemplate 직접 의존) 멀티스레드 통합 테스트를 작성해보고, (b) 같은 로직을 포트/어댑터로 리팩토링한 뒤 동일 테스트를 다시 작성해본다. 두 버전의 테스트 코드량, Testcontainers 의존 여부, 가독성을 비교해 실제로 차이가 유의미한지 판단한다.
  - **프로세스 분리 트리거 (실측 완료):** k6 부하 테스트(SSE 150개 + REST 30 req/s)로 관찰 완료. Tomcat 스레드 점유는 발생하지 않음(SseEmitter = AsyncContext/NIO). 실제 병목은 NIO 커넥션 수 — 운영 규모에서 재실측 예정.
- **관찰 지표:** Prometheus + Grafana로 Tomcat 스레드 풀 사용률, SSE 커넥션 수, REST API 응답 지연을 모니터링한다.
- **전환 조건:** 두 실험/관찰은 서로 독립적으로 다음 Phase 진입을 결정한다. 헥사고날 비교 실험 결과가 먼저 나오면 Phase 1로, 스레드 풀 점유가 먼저 실측되면 (헥사고날 적용 여부와 무관하게) Phase 2로 진행할 수 있다.

### Phase 1: Hexagonal Architecture 전환 (조건부, 단일 모듈 유지)
- **적용 조건:** Phase 0의 비교 실험에서 포트/어댑터 버전이 유의미하게 낫다고 판단된 경우에만 진행한다. 차이가 크지 않다면 이 Phase는 건너뛰고 레이어드를 그대로 유지한다 — 이것도 정당한 결론이다.
- **배포 단위:** 여전히 단일 모듈, 단일 프로세스. Gradle 멀티모듈은 적용하지 않는다 (멀티모듈은 Phase 2의 프로세스 분리 시점에만 의미가 있음).
- **변경 내용:** 핵심 도메인 로직(투표 집계, 중복 투표 방지)을 포트(인터페이스)로 추출하고, Redis/MySQL 구현체를 어댑터로 분리한다. 패키지 구조(`domain/port`, `adapter/out`)만으로 구현하며 빌드 단위는 바꾸지 않는다. 예: `VoteCountPort`(포트) ↔ `RedisVoteCountAdapter`(어댑터).
- **포트폴리오 서사:** "동시성 테스트를 레이어드와 헥사고날 두 버전으로 직접 작성해 비교했고, 그 결과를 근거로 (적용/미적용)을 결정했다"는 비교 실험 과정 자체를 `docs/decisions.md`/`docs/adr/`에 기록한다.

### Phase 2: `vote-push` 프로세스 분리 (실측 후 전환, 이 시점에 모듈 분리도 함께 진행)
- **적용 조건:** SSE 커넥션 증가가 서비스 가용성에 실질적 영향을 미치는 규모로 실측되면 진행한다. ※ Tomcat 스레드 풀 점유 조건은 부하 테스트로 폐기됨 — NIO 커넥션 고갈(max-connections 8192 근접)이 새로운 기준.
- **변경 사항:**
  - 이 시점에 비로소 Gradle 멀티모듈을 적용한다: `vote-core`(도메인) / `vote-api`(MVC, Tomcat) / `vote-push`(별도 실행 단위)로 분리. 모듈 분리의 목적은 "경계를 나누는 것" 자체가 아니라 "vote-push를 별도 프로세스로 띄우기 위한 전제 조건" 충족에 있다.
  - `vote-push`에 `spring-boot-starter-webflux`를 적용하고 독립 프로세스(별도 실행 가능 JAR)로 분리한다.
  - SSE 구현체를 `SseEmitter`에서 `Flux` 기반으로 고도화한다.
  - `vote-api`에서 `vote-push` 의존성을 제거한다. 두 프로세스는 Redis Pub/Sub을 통해 통신한다.
- **모듈 의존성 (분리 시점 기준):**
  - `vote-api` -> `vote-core` (Tomcat 포함)
  - `vote-push` -> `vote-core`, `spring-webflux` (Netty 기반, 독립 실행)
  - `vote-core` -> DB, Redis, Entity 등 인프라 설정 (Web 의존성 완전 배제)
- **정확한 명칭:** Redis/MySQL을 `vote-api`와 계속 공유하므로 "MSA 전환"이 아니라 "SSE 스트리밍 책임의 프로세스 분리"로 표현한다. 완전한 MSA(Database per Service)로 가는 것은 이 프로젝트 규모상 과하다고 판단해 의도적으로 멈춘 지점이라는 점을 서사에 포함한다.
- **배포 환경 제약 (프리 티어 유지):** `vote-api`와 `vote-push`는 별도의 EC2 인스턴스가 아니라, **같은 EC2 인스턴스 안에서 서로 다른 포트로 띄운다.** RDS/ElastiCache도 그대로 공유한다. 이렇게 하면 인스턴스 개수가 늘지 않아 프리 티어 범위를 유지할 수 있다.

## 5. 문서 구조 (Docs Structure)
- `docs/project.md`: 이 파일. 원칙, 스택, 워크플로우 등 거의 바뀌지 않는 메타 정보. 매 세션 항상 로드.
- `docs/decisions.md`: 확정된 의사결정 압축 로그. 매 세션 항상 로드.
- `docs/adr/NNN-제목.md`: 특정 의사결정의 풀버전 디테일(대안 비교, 토론 맥락). 필요할 때만 참조, 평소엔 로드하지 않음.
- **세션 시작 시 권장 로딩 순서:** `project.md` → `decisions.md` (가벼움) → 필요시에만 특정 `adr/*.md` 참조.
